# Security Policy

## Reporting a vulnerability

Please report security issues privately via GitHub's
[private vulnerability reporting](https://github.com/john-athan/sesam/security/advisories/new)
rather than opening a public issue. I'll aim to respond within a few days.

## What Sesam promises

- **A password is fetched, never indexed.** The searchable list holds titles,
  usernames, URLs and vault names. Passwords are read on the keystroke that
  asks for one, and the buffers holding them are overwritten afterwards.
- **Nothing sensitive is ever an argument.** A master password goes to
  `keepassxc-cli` on stdin; new passwords are generated by 1Password and
  KeePassXC themselves. Argument lists are readable by every process on the Mac
  through `ps`, so nothing secret goes in one.
- **Nothing sensitive is written to disk.** The only file Sesam writes is a
  list of salted hashes and counters, and the salt is in the login keychain
  rather than next to them.
- **The clipboard is marked and taken back.** Every write carries
  `org.nspasteboard.ConcealedType` and is cleared on a timer, unless somebody
  else has copied something since.
- **No network, unless you switch on site icons.** Those are off by default,
  and when on they ask each site for its own icon, never a shared icon service.
  Entry URLs are treated as untrusted input: literal addresses and names that
  do not belong to the public internet are refused, and redirects are checked
  again rather than followed.
- **Locking is real.** On sleep, on screen lock, after an idle timeout, or on
  `sesam lock`, the index is dropped and every buffer is wiped. Work that
  started before a lock is discarded rather than published after it.

## Scope notes

Sesam shells out to `op` and to `keepassxc-cli`. External commands are invoked
with arguments passed directly, never through a shell, so an entry's title or
URL cannot inject a command. A compromised copy of either binary is outside
what Sesam can defend against: it is handed a master password.

**A process running as you, against an unlocked Sesam, wins.** Sesam is built
from source and ad-hoc signed, which means it has neither a Developer ID nor
the hardened runtime, so anything running as your user can attach a debugger
and read the decrypted vault out of memory. Every byte buffer and every wipe in
this codebase is defence against something weaker than that. This is stated
plainly rather than mitigated with measures that would only look like a defence:
see `Sources/App/Hardening.swift` and ADR 5.

Two more things are out of scope by construction, both documented in
`docs/adr`:

- Passwords saved by Safari and shown in the Passwords app live in the iCloud
  keychain, behind an entitlement Apple does not issue to third parties. Sesam
  cannot read them and does not try.
- 1Password's `op` session and KeePassXC's own unlocked state belong to those
  programs. Sesam locking itself does not end either one.

The optional "Remember its password, behind Touch ID" setting is off by default
and weakens the KeePassXC setup on purpose: it puts the master password in the
login keychain behind a biometric check that Sesam performs, not one the Secure
Enclave enforces. `Sources/App/TouchID.swift` says exactly what it does and does
not stop.
